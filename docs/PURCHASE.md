# จัดซื้อและตั้งเบิก

เข้าเมนู **จัดซื้อและตั้งเบิก** จาก Sidebar ของ PHARADOL หรือ ADISORN การค้นหา ตัวกรอง วันสร้าง และเลขที่เอกสารยึดเขตเวลา Asia/Bangkok ผู้เสนอใช้บัญชี Studio เดิม ผู้อนุมัติเปิดลิงก์จากอีเมลและยืนยัน OTP ได้โดยไม่ต้องมีบัญชี Studio

## การใช้งาน

1. ผู้ดูแลแบรนด์ตั้งผู้อนุมัติที่เปิดใช้งานหนึ่งคนต่อระดับ เริ่มที่หัวหน้างานระดับ 1 และผู้บริหารระดับ 2 แต่ละระดับใช้อีเมลคนละบัญชี เพิ่มระดับต่อเนื่องได้ถึง 20 ระดับ การเปลี่ยนการตั้งค่าจะใช้กับการส่งรอบใหม่
2. ผู้เสนอสร้างใบตั้งเบิก เพิ่มสินค้า และแนบรูปหรือใบเสนอราคา วันที่รับทั้งปี พ.ศ. และ ค.ศ. ระบบออกเลขเมื่อบันทึกตามวันที่กรุงเทพฯ และใช้ปี ค.ศ. เสมอ รูปสินค้าใช้ JPG, PNG หรือ WebP ส่วนใบเสนอราคาและใบเสร็จรองรับ PDF เพิ่มเติม ไฟล์ละสูงสุด 3 MB
3. กด **ส่งขออนุมัติ** แล้วตรวจลำดับในหน้าเอกสาร ลิงก์ของผู้อนุมัติมีอายุ 3 วัน และต่ออายุได้จากเอกสารเมื่อหมดอายุ OTP มีอายุ 5 นาที ใช้ครั้งเดียว ขอรหัสได้สูงสุด 5 ครั้งต่อลิงก์ เว้น 60 วินาทีต่อครั้ง และกรอกผิดได้สูงสุด 5 ครั้งต่อรหัส
4. เอกสารที่ส่งกลับแก้ไขจะเริ่มจากระดับแรกเมื่อส่งใหม่ เอกสารที่อนุมัติแล้วสามารถเปิดฉบับแก้ไขเพื่อส่งอนุมัติใหม่ก่อนเริ่มจัดซื้อ ดูฉบับที่ส่งในแต่ละรอบได้จากประวัติ
5. ผู้มีสิทธิ์การเงินกด **เริ่มจัดซื้อ** แล้วบันทึกการชำระเงินและใบเสร็จ ยอดซื้อจริงที่สูงกว่ายอดอนุมัติจะเปิดรอบอนุมัติส่วนเพิ่ม เมื่อผ่านทุกระดับจึงปิดรายการ
6. PHARADOL เพิ่มสินค้าที่ซื้อเข้าคลังหรือเชื่อมกับรายการเดิมได้ รายการใหม่ต้องเป็นจำนวนเต็ม คลังใช้หนึ่งชิ้นต่อ Serial Number การเชื่อมรายการเดิมจะบันทึกความสัมพันธ์กับใบตั้งเบิกโดยไม่ปรับจำนวนในคลัง คลังปัจจุบันเปิดให้ PHARADOL เท่านั้น

## สิทธิ์เริ่มต้น

ทุกสิทธิ์อยู่ภายใต้แบรนด์ของบัญชีเดิมและเคารพการปฏิเสธสิทธิ์รายบุคคล

| สิทธิ์ | ค่าเริ่มต้น |
| --- | --- |
| `purchase.view` | ผู้ใช้ทุกบทบาทในแบรนด์ |
| `purchase.write` | STAFF, MANAGER, BRAND_ADMIN, SUPER_ADMIN |
| `purchase.finance` | MANAGER, BRAND_ADMIN, SUPER_ADMIN |
| `purchase.manage` | BRAND_ADMIN, SUPER_ADMIN |
| `purchase.inventory` | MANAGER, BRAND_ADMIN, SUPER_ADMIN ที่มีสิทธิ์เขียนคลัง PHARADOL |

## การติดตั้งและอีเมล

ใช้ Migration `202611240001_purchase.sql` สำหรับใบตั้งเบิกและ Bucket ส่วนตัว และ `202611240002_purchase_equipment.sql` สำหรับเชื่อมคลัง ติดตั้ง Migration คลังที่มีอยู่แล้วในฐานข้อมูลเป้าหมายก่อนติดตั้งไฟล์ที่สอง ใช้ staging Supabase และบัญชีทดสอบสำหรับ Preview

| ตัวแปร | งานที่ใช้ |
| --- | --- |
| `PURCHASE_APP_URL` | Origin ที่ผู้อนุมัติเปิดได้จากอีเมล ต้องใช้ HTTPS บน Vercel |
| `PURCHASE_SECRET` | Secret ฝั่งเซิร์ฟเวอร์อย่างน้อย 32 ตัวอักษร ใช้ลงลายเซ็นลิงก์และ Hash OTP แยกแต่ละสภาพแวดล้อม |
| `PURCHASE_SUPABASE_URL`, `PURCHASE_SUPABASE_SERVICE_ROLE_KEY` | ต้องตั้งสำหรับ Preview ให้ชี้ฐานข้อมูล staging ใน Production ใช้การตั้งค่า Supabase เดิมได้ |
| `PURCHASE_RESEND_API_KEY`, `PURCHASE_TEST_EMAIL` | Preview ต้องใช้คีย์ทดสอบและกล่องจดหมายของผู้ทดสอบ ระบบส่งอีเมลจัดซื้อใน Preview ไปที่กล่องจดหมายนี้ |
| `PHARADOL_EMAIL_FROM`, `ADISORN_EMAIL_FROM` | ผู้ส่งที่ Resend ยืนยันแล้วในแต่ละแบรนด์ ใช้ `RESEND_API_KEY` เดิมได้ใน Production |
| `PHARADOL_EMAIL_REPLY_TO`, `ADISORN_EMAIL_REPLY_TO` | ตั้งได้ตามต้องการ ค่าเริ่มต้นใช้อีเมลติดต่อของแบรนด์ |
| `PURCHASE_CRON_SECRET` | หากตั้งเวลาส่งซ้ำอัตโนมัติ ให้ส่ง GET ไปยัง `/api/purchase/worker` พร้อม `Authorization: Bearer <secret>` ใช้ Secret อย่างน้อย 32 ตัวอักษร |

สถานะ **ผู้ให้บริการรับอีเมลแล้ว** แสดงเมื่อ Resend ตอบรับการส่ง หากการส่งล้มเหลว ผู้ใช้กด **ลองส่งอีกครั้ง** ได้จากหน้าเอกสาร งานส่งผ่านคิวที่บันทึกในฐานข้อมูลและใช้คีย์ idempotency เดิม ภายใน 23 ชั่วโมงแรก หลังจากนั้นสถานะ **รอตรวจสอบการส่ง** ระบุให้ตรวจประวัติที่ Resend ก่อนดำเนินการต่อ

ใช้ `npm test` ตรวจฐานข้อมูลจำลองและ regression ใช้ `npm run build` ตามด้วย `node scripts/purchase-smoke.mjs` ตรวจแอปผ่าน HTTP และ Chromium โดยใช้ PostgreSQL ชั่วคราวและตัวจำลอง Supabase Storage กับ Resend กำหนด `PURCHASE_SMOKE_PDF` เป็น path ในเครื่องเมื่อต้องการเก็บ PDF ตัวอย่างสำหรับตรวจเลย์เอาต์
